01 · The One-Line Version

What this system actually is, in a sentence a judge can repeat back.

This is an agentic procurement system that combines deterministic demand planning, real-time inventory state, vendor intelligence, and an LLM-based decision loop to autonomously resolve kitchen shortages under budget and reliability constraints. Every section below exists to prove one clause of that sentence at a time, so nothing in this deck is decoration.

Deterministic Intelligence
Menu → Requirements → Inventory → Shortage
Handled entirely by Python. Fixed arithmetic, no ambiguity, no model in the loop. This is where correctness has to be guaranteed.
Agentic Intelligence
Shortage → Evaluate → Decide → Act → Replan
Handled by the LLM, once there's an actual trade-off to reason about: price against reliability against budget against availability.

We don't ask an LLM how much rice five hundred students need. Python answers that. The agent only starts once there's a real decision on the table.

07 · The Failure-Recovery Demo

Probably the most important five minutes of the live demo.

Two failure modes, staged on purpose, both recovered without a human touching anything.

Failure Mode 01
Vendor unavailable
Agent checks Vendor A
Vendor A is unavailable
Agent does not attempt the order
Agent evaluates Vendor B instead
Order placed with Vendor B
Failure Mode 02
Order rejected mid-run
Agent selects Vendor A
Places the order
Vendor A rejects the order
Agent receives the failure, state has changed
Re-evaluates remaining candidates, selects Vendor B
Order placed, success

That's actual closed-loop autonomy, not a script that assumes the happy path.

10 · Jury Q&A, Rehearsed

The two questions almost certainly coming.

Question

"Why is this an agent and not just an LLM-powered application?"

Because the LLM isn't generating a recommendation for a human to act on. It operates inside a closed loop with a concrete objective and tools representing the kitchen's real operational state. It observes state, selects an action, executes it, observes the outcome, and replans when the environment changes. It can select a vendor, get rejected, and recover on its own. That's the loop, not a chat reply.

Question

"Why not just give the entire problem to the LLM?"

Because LLMs are probabilistic and inventory quantities, demand calculations, and financial constraints need to be deterministic. We use traditional software wherever correctness is non-negotiable, arithmetic, inventory truth, validation, state, and reserve the agent for exactly the part of the problem that involves genuine trade-offs: vendor evaluation, weighing constraints, deciding, and recovering.

11 · The Elevator Version

"A Next.js frontend backed by a Python FastAPI service. When the kitchen submits a menu and student count, deterministic planning calculates ingredient requirements against persistent inventory. Only genuine shortages reach the procurement agent, which evaluates cost, reliability, availability, and budget through real vendor, inventory, and ordering tools, then executes and observes the result. If a vendor rejects an order, the changed state feeds straight back into the loop and the agent replans. Every decision is persisted and auditable."
